# Naming rules template

```markdown
## Naming system

### Masterbrand
<Name>. Always written as <exact form>. Never abbreviated, never pluralised.

### Products (sub-brands)
Pattern: <Masterbrand> <Name>, e.g. "Acme Ledger"
- One word, two syllables preferred, English, easy to say on a phone call
- Describes the role, not the technology
- Must not be confusable with another product name in the portfolio

### Descriptors
Plain lower-case words that say what something is: "payroll", "invoicing", "app".
Used after the brand or product name: "Acme Ledger invoicing".

### Features
Described, never named. "Automatic tax filing", not "TaxBot".
A feature gets a name only if it passes the new-offer gate.

### Endorsement
"<Name>, by <Masterbrand>". Appears in the logo lockup, app store listing and footer.

### Exceptions
| Name | Rule it breaks | Decision | Reason |
| --- | --- | --- | --- |
```

## The new-offer gate

A team answers these before creating a name. Default: no new name.

1. Is it a product people buy or sign up for separately? If not, it is a feature: describe it.
2. Does it make a promise the parent or an existing product cannot?
3. Would the parent's name help it, or hurt it?
4. Is there budget to support a name for at least three years?
5. Has the name been checked for confusion with existing names, in this portfolio and in the market?

Approver: <role>.

## Naming checks before proposing any name

- Not confusable with another name in the portfolio (spelling, sound, meaning)
- Pronounceable by the core audience on first sight
- Works in the markets where it will be used
- Trademark and domain checks are flagged as still to do; never claim a name is available
